## Use-case 1: Автоматическая обработка и классификация ответа

**Предметная область:** _Формы «Откликнись»_

**Первичный актор:** _Система_

**Вторичные акторы:** 
* Очередь входящих сообщений (Queue)
* Гео-сервис
* Антиспам/Детектор аномалий
* База данных ответов (Response Database)
* База данных форм (Form Schema Database)
* Сервис уведомлений (Notification Service)

**Цель**: _Входящий ответ респондента классифицирован как «качественный» или «отписка», обогащен контекстными метаданными (гео, устройство, время) и доступен для построения аналитических отчетов._

**Предусловия**: 
* В очереди сообщений есть необработанные ответы
* База данных форм доступна (нужна схема, чтобы знать типы полей)
* Гео-сервис доступен
* Система имеет достаточно ресурсов для обработки

**Основной поток** (Happy Path):
1. Обработчик очереди получает событие «Новый сырой ответ» из очереди.
2. Обработчик извлекает пакет с `response_id`, `form_id`, `answers` и `metadata`.
3. Обработчик запрашивает из БД схему формы для валидации типов полей.
4. Обработчик валидирует каждый ответ под тип поля (число, текст, рейтинг).
5. Обработчик обращается к Гео-сервису для определения страны и города по IP.
6. Обработчик парсит User-Agent для определения устройства (мобильный/десктоп, ОС, браузер).
7. Обработчик вычисляет время заполнения (`submitted_at` - `started_at`).
8. Обработчик передаёт данные в Антиспам-движок для проверки качества.
9. Антиспам-движок возвращает `quality_score` и флаг `is_suspect`.
10. Обработчик сохраняет обогащённые данные в Базу данных ответов.
11. Обработчик проверяет триггеры уведомлений для этой формы.
12. Обработчик удаляет обработанное сообщение из очереди.
13. Система логирует успешную обработку с метриками.

**Постусловия**:
* В Базе данных ответов создана запись с обогащёнными метаданными
* К ответу привязаны гео-данные и информация об устройстве
* Ответ помечен как «качественный» или «отписка» с указанием причины
* Исходное сообщение удалено из очереди

**Альтернативные потоки**:

### 5a. Гео-сервис недоступен

**Условие:** На шаге 5 Гео-сервис не отвечает в течение 3 секунд

**Поток:**
1. 5a1. Обработчик ловит TimeoutException
2. 5a2. Обработчик логирует предупреждение «GeoIP service unavailable»
3. 5a3. Обработчик продолжает обработку без гео-данных (поля geo остаются null)
4. 5a4. Обработчик помечает ответ тегом `geo_enrichment_failed: true`
5. 5a5. Переход к шагу 6 основного потока

### 9a. Ответ признан подозрительным (отписка)

**Условие:** На шаге 9 Антиспам-движок возвращает `is_suspect = true` (время заполнения 5 секунд)

**Поток:**
1. 9a1. Антиспам-движок возвращает `quality_score = 0.15` и `suspect_reason = "filling_time_too_short"`
2. 9a2. Обработчик добавляет флаг `is_suspect: true` и причину в метаданные
3. 9a3. Обработчик сохраняет ответ в специальную «карантинную» секцию БД
4. 9a4. Обработчик НЕ учитывает этот ответ в агрегированных метриках формы
5. 9a5. Переход к шагу 10 основного потока

### 11a. Сработал триггер уведомления

**Условие:** На шаге 11 система обнаруживает, что для формы настроено правило «Уведомлять, если рейтинг < 3»

**Поток:**
1. 11a1. Обработчик проверяет ответ: рейтинг = 2 (ниже порога 3)
2. 11a2. Обработчик создаёт событие «TriggerFired» с параметрами
3. 11a3. Обработчик отправляет команду в Сервис уведомлений
4. 11a4. Сервис уведомлений подтверждает получение команды
5. 11a5. Переход к шагу 12 основного потока

**Исключительные ситуации**:

### 2a. Схема формы не найдена в БД

**Условие:** На шаге 3 форма с ID `FORM-42` не найдена

**Поток:**
1. 2a1. Обработчик получает исключение «Form not found»
2. 2a2. Обработчик помещает ответ в очередь «Dead Letter Queue» с тегом `orphan_response`
3. 2a3. Обработчик логирует критическую ошибку
4. 2a4. Обработчик отправляет алерт администратору
5. 2a5. Use-case завершается неудачей

### 4a. Несоответствие типов данных

**Условие:** На шаге 4 в поле «rating» пришла строка «abc» вместо числа

**Поток:**
1. 4a1. Обработчик пытается привести тип (string → int)
2. 4a2. Приведение невозможно
3. 4a3. Обработчик помечает ответ как `malformed`
4. 4a4. Обработчик сохраняет сырые данные в таблицу `parse_errors`
5. 4a5. Обработчик удаляет сообщение из очереди (чтобы не блокировать)
6. 4a6. Use-case завершается с ошибкой

### 10a. База данных ответов недоступна

**Условие:** На шаге 10 БД не отвечает

**Поток:**
1. 10a1. Обработчик ловит ConnectionException
2. 10a2. Обработчик НЕ удаляет сообщение из очереди (останется для повторной попытки)
3. 10a3. Обработчик логирует ошибку
4. 10a4. Обработчик отправляет алерт
5. 10a5. Use-case завершается неудачей

## Use-case 2: Настройка правил детекции отписок

**Предметная область:** _Формы «Откликнись»_

**Первичный актор:** _Автор формы_

**Вторичные акторы:**
* API конструктора (Builder API)
* Database (Хранилище настроек форм)

**Цель:** _Определить критерии, по которым система будет автоматически отличать осмысленные ответы от отписок._

**Предусловия:**
* Пользователь авторизован
* У пользователя есть хотя бы одна созданная форма
* База данных доступна

**Основной поток** (Happy Path):
1. Пользователь переходит в раздел «Настройки → Антиспам» для выбранной формы.
2. Система отображает текущие правила детекции со значениями по умолчанию.
3. Пользователь устанавливает минимальное время заполнения: «30 секунд».
4. Пользователь устанавливает минимальную длину текста в открытых вопросах: «10 символов».
5. Пользователь включает опцию «Блокировать повторяющиеся символы (аааа, 123)».
6. Пользователь нажимает «Сохранить настройки».
7. Система проверяет, что все значения в допустимых диапазонах.
8. Система сохраняет правила в БД с привязкой к форме.
9. Система выводит сообщение: «Правила детекции отписок сохранены».

**Постусловия**:
* В Базе данных создана запись о правилах детекции для формы
* При последующей обработке ответов система будет применять эти правила

**Альтернативные потоки**:

### 3a. Сброс настроек по умолчанию

**Условие:** Пользователь хочет вернуть стандартные правила

**Поток:**
1. 3a1. Пользователь нажимает кнопку «Сбросить настройки»
2. 3a2. Система запрашивает подтверждение
3. 3a3. Пользователь подтверждает
4. 3a4. Система восстанавливает значения по умолчанию (мин. время = 15 сек, мин. длина = 3 символа)
5. 3a5. Переход к шагу 8 основного потока

### 5a. Настройка исключений

**Условие:** Пользователь хочет добавить доверенные IP-адреса, которые не проверяются

**Поток:**
1. 5a1. Пользователь переходит во вкладку «Белый список»
2. 5a2. Пользователь вводит IP-адрес «77.88.55.66» и нажимает «Добавить»
3. 5a3. Система проверяет валидность IP-формата
4. 5a4. Система сохраняет IP в белый список
5. 5a5. Переход к шагу 6 основного потока

**Исключительные ситуации**:

### 7a. Некорректное значение времени

**Условие:** Пользователь ввёл минимальное время заполнения «1000 секунд» (> допустимого)

**Поток:**
1. 7a1. Система подсвечивает поле красным
2. 7a2. Система показывает сообщение: «Минимальное время заполнения не может превышать 300 секунд (5 минут)»
3. 7a3. Возврат к шагу 3

**Условие:** На шаге 8 произошёл разрыв соединения

**Поток:**
1. 7b1. Система получает Connection Error
2. 7b2. Система показывает сообщение: «Ошибка связи с сервером. Настройки не сохранены»
3. 7b3. Use-case завершается неудачей

## Use-case 3: Просмотр отчёта с фильтрацией отписок

**Предметная область:** _Формы «Откликнись»_

**Первичный актор:** _Автор формы_

**Вторичные акторы:**
* API отчётов (Reporting API)
* Database (Хранилище ответов)

**Цель:** _Получить агрегированную статистику по ответам, исключая подозрительные («отписки») для принятия обоснованных решений._

**Предусловия:**
* У формы есть хотя бы один ответ
* База данных доступна

**Основной поток** (Happy Path):
1. Пользователь переходит в раздел «Отчёты» для выбранной формы.
2. Система отображает дашборд со сводной статистикой.
3. Пользователь замечает, что средний рейтинг = 4.8, но комментарии полны жалоб.
4. Пользователь включает тумблер «Скрыть подозрительные ответы (отписки)».
5. Система пересчитывает статистику без учёта ответов с флагом `is_suspect = true`.
6. Система отображает обновлённые данные: средний рейтинг падает до 3.2.
7. Система показывает уведомление: «Исключено 47 подозрительных ответов (12% от общего числа)».
8. Пользователь нажимает «Экспортировать отчёт».
9. Система генерирует CSV-файл с чистыми ответами.
10. Система инициирует скачивание файла.

**Постусловия:**
* Пользователь получил агрегированную статистику без учёта отписок
* CSV-файл с чистыми ответами сохранён на устройство пользователя

**Альтернативные потоки**:

### 4a. Просмотр только подозрительных ответов

**Условие:** Пользователь хочет проверить, какие именно ответы были отфильтрованы

**Поток:**
1. 4a1. Пользователь нажимает «Показать только отписки»
2. 4a2. Система отображает таблицу с подозрительными ответами и причинами их отметки
3. 4a3. Пользователь видит, что большинство отписок пришло с одного IP
4. 4a4. Пользователь нажимает «Добавить IP в чёрный список»
5. 4a5. Переход к шагу 8 основного потока

### 4b. Ручное исправление классификации

**Условие:** Пользователь считает, что система ошибочно пометила хороший ответ как отписку

**Поток:**
1. 4b1. Пользователь находит ответ в таблице «Подозрительные»
2. 4b2. Пользователь нажимает «Отметить как качественный»
3. 4b3. Система меняет флаг `is_suspect` с `true` на `false`
4. 4b4. Система пересчитывает статистику
5. 4b5. Система сохраняет действие в лог аудита
6. 4b6. Переход к шагу 8 основного потока

**Исключительные ситуации**:

### 2a. Нет ответов для отображения

**Условие:** У формы нет ни одного ответа

**Поток:**
1. 2a1. Система показывает сообщение: «Нет ответов для отображения. Поделитесь ссылкой на форму!»
2. 2a2. Система отображает кнопку «Получить ссылку для публикации»
3. 2a3. Use-case завершается успешно (без данных)

### 5a. Ошибка пересчёта статистики

**Условие:** На шаге 5 произошла ошибка при агрегации данных

**Поток:**
1. 5a1. Система ловит исключение
2. 5a2. Система показывает сообщение: «Не удалось загрузить отчёт. Попробуйте позже»
3. 5a3. Use-case завершается неудачей
